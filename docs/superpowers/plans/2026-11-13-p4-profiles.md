# P4: Profiles, on a raised mise floor, Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One Mac, or one user across Macs, switches between named variants such as personal and work with `rotm settings profile list|use|new`, and switching back restores what was there.

**Architecture:** A profile is a mise config environment named `rotm-p-<name>`, selected by the `env` line of `miserc.local.toml`. Its settings live in mise's per-environment override file, `config.rotm-p-<name>.override.toml`, which mise ranks above the shared `config.override.toml`, so a profile holds only what differs and everything else falls through to the shared settings. The two things mise cannot hold per environment, the module off list and `tools.toml`, get a per-profile file each. Tasks 1 to 3 come first. Task 1 fixes a defect this plan's research found in shipped code, and it can land today on the current floor. Tasks 2 and 3 are the owner's request of 2026-11-13: raise the mise floor to 2026.11.8 and move the macOS preferences to mise's new `[bootstrap.settings.macos]` tables.

**Tech Stack:** bash 3.2 (`bin/lib/*`), zsh, Python 3.11+ standard library (`settings/`), mise 2026.11.8, real-mise self-checks in scratch homes.

**Spec:** `docs/superpowers/specs/2026-11-11-installable-setup-profiles-and-sync.md`. Read its Goal and "Decisions the owner made" in full before Task 1. This plan implements the P4 brief and the spec's "Profiles" section.

## Global Constraints

- macOS only (decision 4).
- mise floor: 2026.11.8 after Task 2 (`setup/mise-floor.sh`, `settings/src/dotfiles_settings/mise.py`, `.github/workflows/check.yml`). Before Task 2 it is 2026.11.5, and Task 1 must pass on it.
- Where mise can hold a setting, mise holds it (decision 14). A profile's settings go in mise's own per-environment override file. We build only the per-profile module list, the per-profile `tools.toml`, the links and the guards.
- Nothing leaves the base (decisions 3 and 12). No task removes a package, a default or an owner-pointing value.
- An installed copy stays fast-forwardable: no command writes a tracked file of the checkout. A profile's files are created in `~/.config/rotm` and linked from the config dir before mise first writes them. Measured: with no file present, `mise set --override --env` creates it inside the config dir, which on an installed copy is the checkout.
- Sync stays manual (decision 8). Which profile a Mac uses is in `miserc.local.toml`, which mise never syncs, so the choice is per Mac. Every profile's files sync.
- A profile's environment name is `rotm-p-<name>`. Measured: a name in the saved `env` list also loads a project's `mise.<name>.toml`, so a bare `work` would pull in a project's `mise.work.toml`.
- `default` is the reserved name for "no profile": the shared settings alone.
- The owner's Mac is a development clone. Never run `./setup.sh`, `sysup`, `rotm install`, `rotm update`, `rotm settings sync on`, `rotm settings profile use|new`, `mise bootstrap` or `rotm-modules set|sync` against the real home. Self-checks use stubs and scratch homes, with `HOME` and every `MISE_*_DIR` pointed at the scratch folder and every mise call run from the scratch home.
- The self-checks have their own helpers (`run`, `prepare`, `check_true`, `has`, `lacks`, `stub`, `$STATE`, `$fix`; `raises` in the Python tests). Where a block here and the file disagree on a helper, the file wins and the assertion stays.
- A new bash self-check is one `job quiet bash <path>` line in `bin/lib/check`, and a new stdlib Python test one entry in `settings_tests` there.
- `pnpm check` runs before every commit. Edit and commit in separate Bash calls. One commit per task, with the subject the task names.
- Docs mirror behaviour: a change to setup or settings behaviour has its `README.md`, `setup/README.md`, `settings/README.md` or `docs/` edit in the same commit. A docs page is never named after a command.

## Decided while writing this plan

**Where `rotm settings set` writes while a profile is active.** To the active profile. `--shared` writes the shared settings instead. With no profile active, every write is shared.

The owner asked on 2026-11-13 what the recommended practice is. Three reasons, in order of weight:

1. The spec names VS Code's Settings Sync as the model. VS Code's profiles documentation (`docs/configure/profiles.md` in `microsoft/vscode-docs`, read 2026-11-13) records a change in the current profile, and offers "Apply Setting to all Profiles" as the action a user takes to share one.
2. It is the only default where a `set` always takes effect. mise ranks the profile's override file above the shared one, so a shared write is invisible in a profile that already sets that key.
3. mise's own `mise set` goes the other way (shared unless `--env`), but that default serves a repository's committed config, where the shared file is the team's. Here both files are one person's.

When `--shared` writes a key the active profile also sets, the command says so and names `rotm settings reset <id>`, which removes the profile's value. It does not delete the profile's value itself.

**A profile's module list is its own copy.** `profile new` copies the shared off list. mise reads `ignored_config_paths` only from `miserc` files, which have no per-environment form, so module switches cannot fall through the way settings do.

**mise writes the `env` line when it can.** `mise -E <names> bootstrap --save-env --only final-hook` writes the line, keeps the rest of the file and applies nothing. It cannot write an empty list (measured: it errors with no `-E`), so leaving the last profile on a clone removes the line with our own edit.

**Running the install line again deselects the profile.** The line in `README.md` and `docs/installation.md` passes `-E rotm-installed --save-env`, and `-E` replaces the saved list. `rotm update` and `rotm install` pass no `-E`, so they keep it, and they are the documented way to rerun. The plan does not change the install line: Task 11 documents it, and `profile list` shows `default` as active afterwards, so nothing is lost and one `profile use` restores it.

**Out of scope.** `profile delete` and `profile rename` (remove or rename the three files by hand; the history keeps old versions). Per-profile `[dotfiles]` variants: mise supports `variants = [{ profile = "<env>" }]`, and no shipped file needs one yet. Showing the active profile in the terminal and browser UIs: their writes already go through the adapters, so they follow the active profile, and the display belongs to P5.

## Review Focus

1. A shell with `MISE_ENV` or `-E` set. mise uses it in place of the saved list, so the profile is not in effect there. `profile list` says so instead of showing the saved profile as active (Task 4).
2. A hostile or reserved profile name: `Work`, `my work`, `../x`, `default`, an empty string, 40 characters. `profile new` refuses each with exit 2 and creates nothing (Task 4).
3. The saved `env` line names a profile whose files are not on this Mac (a restore that has not run, a file removed by hand). Reads fall back to the shared settings and `profile list` names the missing profile; a write refuses rather than creating a file inside the checkout or changing the shared list (Tasks 4, 5 and 6).
4. A secret-named key or a single-Mac setting in a profile's override file. `sync on` and `sync now` refuse and name that file, as they do for the shared one (Task 7).
5. An `env` line the user edited: other environment names, or a list split across lines. Other names are kept in their order, and a multi-line list is refused with the file left alone (Task 4).

- [x] **Step 3: Implement.** Run `"$mise" env -s zsh -C $HOME`, and do not filter its output by line: a multi-line value spans lines (`export D_ML='a` then `b'`), and keeping only the `export <KEY>=` lines leaves an unterminated quote that breaks every later shell. Evaluate the output in a subshell and print each collected key that is set:

  ```zsh
  ( eval "$out"
    for k in $keys; do (( ${(P)+k} )) && print -r -- "export $k=${(qq)${(P)k}}"; done
  ) >| $cache.$$ && command mv -f $cache.$$ $cache
  ```

  Measured in zsh 5.9: a two-line value and `it's "x" #y` both came back byte for byte, and `PATH` from the output did not reach the calling shell. The `shortcut:` comment goes.
