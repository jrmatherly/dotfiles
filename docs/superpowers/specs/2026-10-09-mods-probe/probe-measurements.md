## Settled open questions
1. `next(e)` on `classic.UserPromptSubmit` resolves to `{ additionalContext: [string, ...] }` (1401 and 2204 chars in the two prompts; the prompt-improver plugin's PROMPT EVALUATION text was the first element). On `classic.SessionStart` it resolved to `{ additionalContext: [...] }` of 3652 chars (superpowers text first). On PreToolUse, PostToolUse and Stop it resolved to `{}`. A mod can therefore see every settings hook's injected context and its size. Context ledger: feasible.
2. Hook additionalContext reaches the model as a `prompt.attachment` event with `type: 'hook_additional_context'` and `origin: { kind: 'hook', event: 'UserPromptSubmit' | 'SessionStart' | ... }` (types file claude-code.d.ts, PromptAttachmentOrigin). The origin names the event, not the hook; the text identifies the source (e.g. `<codegraph_context`). A `prompt.attachment` hook may return `{ text }` to rewrite or `{ text: null }` to drop it. Other attachment types seen in this run: `model`, `deferred_tools_delta`, `total_tokens_reminder`. So a mod can drop or shrink the codegraph miss injection and any other hook's context, and can size them per turn.
3. The tool-call id field on `tool.call`, `tool.check` and `classic.PreToolUse` is `tool_use_id` (30-char string). `tool.call` keys for Bash: command, description, tool, tool_use_id. For Agent: description, subagent_type, model, prompt, tool, tool_use_id. `tool.call` result for Agent includes `result.agentId`, `result.resolvedModel`, `result.outputFile`, `result.isAsync`, `result.status`.
4. MCP tool search is active: a `deferred_tools_delta` attachment was sent in the subagent's first request. `isDeferred: false` on the jstack `step` tool matters.
5. Classic hook batch times in this run (ms inside `await next(e)`, all hooks of that event, with every installed plugin on): SessionStart 6773, UserPromptSubmit 202 and 168, PreToolUse 40, PostToolUse 179, Stop 542. A latency meter is a 10-line hook.
6. `agent.spawn` event keys: tool_use_id, prompt, description, subagentType, provider {plugin, tier}, model ('haiku', the requested alias), parentModel (full id), permissionMode, background, fork, name, cwd. Result: { model (resolved full id), agentId }. A mod can set or veto the model per spawned role. 
7. `turn.step` keys: turnId, index, model (full id), effort, messageCount, agentId (subagent requests only). The docs say a hook may return `next({ ...e, model })` or `next({ ...e, effort })`, so per-request model and effort override is available (not exercised).

11. `$.session.version()` returns { version, base, builtAt }. `$.session.surfaces()` returned [] in -p. `$.session.model()` returned the model id.
12. `claude plugin validate` is strict static analysis: it rejects `on(ev, hook)` where `ev` is a variable, rejects a hook produced by a factory call (must be a function literal or the name of a function), rejects `.catch` on `turn.step` unless the hook is an async generator, and requires `$` calls spelled `$.noun.method(...)` at the call site. Loops over event names do not validate. This shapes how a multi-event mod must be written (one named function per event).
13. In `-p` sessions Claude Code 2.1.295 does not write `.claude-plugin/types/` for a `--plugin-dir` mod (changelog 2.1.295); the committed `~/dev/skills/jstack/types/claude-code.d.ts` (21,283 lines, "Written by Claude Code 2.1.295") is the ground truth.
